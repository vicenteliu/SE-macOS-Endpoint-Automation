# Phase 3 — the files that ran

**As run — one machine, one afternoon, two applications, no fleet.** These are the files the
phase-3 runbook's verification rows were produced from, copied out of the repository and the
override directory after the run, not written for this page. Nothing here was authored from
scratch: the overrides were taken from community recipes, the item metadata was generated by the
import tool and by the packaging chain, the manifest was made by the manifest tool. Where the
runbook says a command *appears wherever a lab tier can produce it*, this directory is the
minimum tier producing it.

⛔ Not claimed, because not run: a second client · a scheduled run · authentication or TLS on the
repository · a recipe authored from scratch · trust verification as a gate in anger · a catalog
other than `testing`. The runbook's *Acceptance* section says the same.

## Before you start

- **Host**: one machine, macOS 26.6.2, the client tool at 7.3.0 and the packaging automation at
  2.9.0 — the current **stable** release, not the newest tag (the runbook's Hop 3 says why).
- **Repository**: a directory with `catalogs/ icons/ manifests/ pkgs/ pkgsinfo/`, symlinked into
  the system web server's document root and served by the Apache that ships with macOS.
- **Two applications**: one already installed at an **older** version than the repository will
  offer (here: a browser at 155.0), and one not installed at all (here: a file-transfer client).
  The first is what makes the acceptance mean something.

## Permissions

- An administrator account on the machine, for `sudo` on the client run and for the web-server
  symlink. No directory service, no MDM, no identity provider — none is needed for this phase and
  none was present.
- Outbound HTTPS to the two vendors' download hosts and to the recipe repository host, for the
  packaging chain. Nothing inbound.
- The account that ran the tools is recorded in each pkginfo's `_metadata.created_by`. **That is
  the one field edited here**: the account name is replaced with `lab-user`. Every other byte is
  as generated.

## Minimum test

One item that is already installed at an older version, offered at a newer one, on a machine
where nobody touches the application. If it upgrades on its own, the model works; a first
install proves only the transport. That is the runbook's acceptance and it is the smallest thing
that proves it.

## Verify

The rows from the runbook, with what these files produced.

| | Command | Seen |
|---|---|---|
| 1 | `curl -so /dev/null -w '%{http_code}' http://localhost/<repo>/catalogs/testing` | `200`; the repository root itself `403` — indexing off, not a fault |
| 2 | client run with the browser **open** | [`logs/ManagedSoftwareUpdate.log.excerpt`](logs/ManagedSoftwareUpdate.log.excerpt): `Blocking apps for Firefox are running: ["Firefox.app"]` → `Skipping install of Firefox because blocking applications are running.` The pkginfo carries **no** `blocking_applications` key; the client derived it from the `installs` array's `path` |
| 2 | client install run with the browser **closed** | [`logs/Install.log.excerpt`](logs/Install.log.excerpt): `Install of Mozilla Firefox-155.0.1: SUCCESSFUL` — it was at 155.0 |
| 2 | the same run, the item that was not installed | `Install of Cyberduck-9.5.4: SUCCESSFUL` |
| 3 | one packaging run over the two overrides plus the catalog rebuild | [`pkgsinfo/Firefox-155.0.1.plist`](pkgsinfo/Firefox-155.0.1.plist) and [`pkgsinfo/Cyberduck-9.5.4.plist`](pkgsinfo/Cyberduck-9.5.4.plist) generated, [`catalogs/testing.plist`](catalogs/testing.plist) rebuilt with three items; the chain `URLDownloader → EndOfCheckPhase → Unarchiver → CodeSignatureVerifier → DmgCreator → MunkiPkginfoMerger → MunkiImporter → MakeCatalogsProcessor` in the run output |

To reproduce with these files: put the two overrides in the override directory, the manifest in
`manifests/`, run the packaging chain over the two override names plus the catalog recipe, then
the client with `--installonly`. The 154.0 pkginfo is the manual import that preceded the chain
and is kept because the runbook's Hop 1 is the manual import.

## Rollback

Everything in the runbook's *Teardown*: remove the web-server symlink and the repository
directory, the client and its `Managed Installs` directory, the packaging tool and its override
and recipe-repository directories, and the two preference domains. The two applications the run
installed are removed with the client's own uninstall (both items are `uninstallable`, method
`remove_copied_items`) or by deleting them from `/Applications`.

## What is in each file

| File | Made by | What to look at |
|---|---|---|
| `overrides/Firefox.munki.recipe` | `autopkg make-override` | `ParentRecipeTrustInfo` — the pinned git hash and SHA-256 of every parent recipe and non-core processor. **This block is the supply-chain control**; a parent that changes upstream fails trust verification until a person re-pins it |
| `overrides/Cyberduck.munki.recipe` | same | The same block, with an empty `non_core_processors` — the vendor feed is read by a core processor |
| `pkgsinfo/Firefox-154.0.plist` | manual import (`munkiimport -n`) | The `installs` array keyed on `CFBundleShortVersionString` at `/Applications/Firefox.app` — the version-comparison key |
| `pkgsinfo/Firefox-155.0.1.plist` | the packaging chain | The same array, one version up; no `blocking_applications` key, yet the client refused to replace a running app. **The array does two jobs** |
| `pkgsinfo/Cyberduck-9.5.4.plist` | the packaging chain | A first install: same shape, `minimum_os_version` from the bundle |
| `manifests/site_default.plist` | `manifestutil` | Two names under `managed_installs`, one catalog. The client fetches this by its own name or falls back to `site_default` |
| `catalogs/testing.plist` | the catalog rebuild | The three pkginfo dicts concatenated; what `curl …/catalogs/testing` returns with `200` |
| `logs/*.excerpt` | the client | Twelve lines and two lines, unedited except for being cut out of longer logs |
